---
title: Deploy on Jio
description: Create a fresh 4-vCPU deployment and print its public URL.
---

Choose **Large (4 vCPU, 8 GiB)** in `jio config`. The deployment script remembers its VM in `.local/jio-vm`, reuses its Docker build cache on later runs, starts every service, and checks the public endpoints.

```bash
./deploy/jio.sh
```

Progress and the complete endpoint list are written to stderr. The final stdout line contains only the landing URL, so it can be captured directly:

```bash
landing_url="$(./deploy/jio.sh)"
open "$landing_url"
```

Pass an existing Large computer ID to select it for this and future deploys:

```bash
./deploy/jio.sh <vm-id>
```

The script uses the current Git branch and its `origin` remote. Override either value when needed:

```bash
GIT_REPO=https://github.com/you/project.git GIT_REF=feature ./deploy/jio.sh
```

Set `DEPLOY_IMAGE` to skip compilation on the VM and pull an existing image:

```bash
DEPLOY_IMAGE=ghcr.io/you/project:sha ./deploy/jio.sh
```

Pushes to `main` run the included GitHub Actions workflow. It builds the image with GitHub's layer cache, pushes it to GHCR, then deploys it to the same VM. Configure repository secrets `JIO_API_KEY` and `JIO_SSH_KEY`, plus bootstrap variables `JIO_ENDPOINT`, `JIO_VM_ID`, and `JIO_HOST_KEY`. The workflow keeps the current non-secret VM identity in the `jio-state` Git tag, recreates a deleted VM with the same deployment SSH key, and remembers its replacement automatically.

The computer keeps its PostgreSQL volume and OAuth signing keys across redeployments. Destroying the computer removes that state and gives the next deployment new public URLs.

## Connect a client

Open the printed **App** URL, register, and select a project. Then follow [Connect ChatGPT and Claude](../clients/connect.mdx) with the App URL plus `/mcp`.
